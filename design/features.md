# Features

What Vertical Docs does, in the words of someone who uses it. One line per feature, grouped by who benefits. A built line ends with its proof: a number, a test or a command. A planned line names its phase in the [plan](architecture.md).

Every phase updates this list. Write nothing here that a tool result has not shown.

## For readers

- **Fast pages** (built). Lighthouse scores 100 for performance, accessibility, best practices and SEO, and CI fails a change that drops below 100, or below 95 for performance. Proof: five pages scored 100 in all four categories in each of three runs (local run on the phase 2 build, 2026-11-17); the scores CI enforces are in `lighthouserc.json`. On real content: five pages of the vAPI docs and five of the Vertical Studio docs, among them the longest page and the page with the most screenshots, scored 100 in all four categories in each of three runs, with a layout shift of 0 (local run on the phase 3a build, 2026-11-17). With the canonical URL, the share tags, the structured data and `robots.txt` of phase 3b, five pages of the vAPI docs again scored 100 in all four categories in each of three runs (local run, 2026-11-17).
- **Tiny downloads** (built). A page loads 2.9 KB of CSS and 1.2 KB of JavaScript, gzipped. A site over the budget of 4 KB and 1.25 KB fails the check. Proof: `scripts/check-dist.ts` and its tests; 2,479 and 1,208 bytes measured on the phase 3b build, 2026-11-17 (the CSS grew by 26 bytes with the longer font addresses). The JavaScript budget was 1 KB until the copy buttons. With the header tabs: 2,621 and 1,211 bytes, from 2,468 and 1,208 (2026-11-19); the 3 bytes of JavaScript are a longer selector, and the tabs themselves are links. With the home page layout: 2,898 and 1,211 bytes (2026-11-20).
- **Search that opens the right section** (built). Press `/`, `⌘K` or `Ctrl+K`, type a word, and the result opens the page at the heading that matched, also for a word that appears only under a small heading. Proof: the test "a word that appears only in an h3 section finds that section first" in `src/core/search.test.ts`; in Chrome, typing `indented` gave one result and opened `/reference/markdown/#a-part-of-a-section` (2026-11-17).
- **Search forgives typing** (built). The first letters of a word are enough, and a small typing mistake still finds the word. Proof: the test "finds a word from its first letters and through a typing mistake".
- **Search costs nothing until it is used** (built). A page downloads no search code. The first time search opens, the browser fetches 6.1 KB of search code, gzipped, and the index. Proof: the request log of the built site shows the search worker and `search.json` only after the first open (2026-11-17); a site with more than 8 KB of on-demand JavaScript fails the check.
- **Search works from the keyboard** (built). `Enter` opens the first result, `Tab` moves through the others, `Esc` closes, and a Close button serves phones. Proof: driven with key presses in Chrome, 2026-11-17.
- **Search speaks to screen readers** (built). The input is labelled and the number of results is a status message. Proof: the status element holds "9 results" after a query in Chrome (2026-11-17); not tested with a screen reader.
- **The best page first** (built). A page with the word in its title leads, and one page cannot fill the list on its title alone. Proof: the test "a section does not outrank other pages on the title of its page alone".
- **Works without JavaScript** (built). Every page is complete static HTML, and the sidebar groups open and close without a script. JavaScript only switches the theme, opens the search, copies, and scrolls the sidebar to the current page. Proof: the page text is in the files in `dist/`; the only scripts are the three inline ones `check-dist` measures.
- **Light and dark theme** (built). The theme follows the system and remembers a choice, with no flash on load. Proof: phase 1 screenshots in both themes; the saved choice is applied by an inline script before the first paint.
- **Readable code blocks** (built). Every code colour passes the 4.5:1 contrast minimum in both themes. Proof: measured in phase 1.
- **Mobile navigation with no JavaScript** (built). The sidebar opens with the Popover API. Proof: phase 1.
- **A sidebar that holds a hundred pages** (built; Safari not tested). A folder is a group that opens and closes; the groups around the current page are open and the sidebar scrolls to that page, on a phone when the menu opens. Proof: the vAPI docs, 109 pages three levels deep, show 16 entries with every group closed, and the Vertical Studio docs, 47 pages four levels deep, show 9; on the deepest page the current entry is in view in a window 800 and 640 pixels high and on a 375 by 667 phone (measured in Chrome, 2026-11-17); in Firefox 161 the groups open and close and the current entry is in view, also in the phone menu; the same in WebKit 26.6, the engine of Safari (2026-11-18).
- **Header tabs for a site with sections** (built; Safari itself not tested). A site that lists top-level folders as `tabs` in `docs.config.json` gets them as tabs in the header, after a first tab "Overview" for every other page, and the sidebar shows only the pages of the tab being read. A site that lists none keeps its one sidebar. On a phone the tabs are in the menu, so the page is as it is without tabs. Previous and next stay inside a tab, and the tabs add no script. Proof: the eight tests of `navigation` in `src/core/nav.test.ts`. The vAPI docs with six folders listed build 110 pages with seven tabs: the sidebar of the Call tab has 7 entries with every group closed where the one sidebar has 16, a page carries 27 sidebar links where it carried 109, and the pages together are 2.1 MB of HTML where they were 2.8 MB. At 1280 pixels wide the header is 100 pixels high with the row of tabs in its last 44, and the sidebar starts under it, in Chrome 157, Firefox 161 and WebKit 26.6; at 390 pixels the header stays 56 pixels high, the menu holds the seven tabs, and on the deepest Call page the current page is in view when the menu opens, in Chrome and WebKit (Firefox the same at 500 pixels, its narrowest window). Seven tabs take 456 of the 848 pixels the row has at 896 pixels wide, and eleven take 835; a row that does not fit is not handled. Lighthouse scored 100 in all four categories on five pages of that build in each of three runs, with a layout shift of 0. `sitemap.xml` of that build is the file of the build without tabs, and `llms.txt` and the 703 records of `search.json` differ only in the title of the one page the trial renamed from "What is Call" to "Call", to name its tab. Without `tabs`, the 48 pages of the Vertical Studio docs, the 110 of the vAPI docs and the kit's own 15 are the same files as before the change, byte for byte, once the name of the stylesheet and the one selector in the page script are set equal. From an installed tarball, `vertical-docs check` exits 0 on the vAPI docs (110 pages), on the Vertical Studio docs (48) and on the vAPI docs with tabs (110) (all 2026-11-19).
- **A home page for a site** (built; live on verticaldocs.dev; Safari itself not tested). A site that sets `home` in `docs.config.json` gets its first page as a home page: one centred column under a large title, without the sidebar, with the first code block as the command to start with, a list as a grid and a "Docs" link in the header. The page is plain Markdown, so it has its Markdown copy, its search records and its line in `llms.txt`, and no other page lists it in the sidebar. A site that does not set it is as before. Vertical Docs' own first page is one: "Docs that live in your repository", with the install line `npx vertical-docs init`. Proof: the test "a site whose first page is a home page leaves that page out of every sidebar, so the first page after it has no previous page" in `src/core/nav.test.ts`. On the kit's own build the home page has the same layout in Chrome 157, WebKit 26.6 and Firefox at 1280 pixels and at a phone's width, the Copy button copies `npx vertical-docs init` without the `$`, and the search opens from it (2026-11-20). Lighthouse scored 100 in all four categories on the home page and on two docs pages in each of three runs, with a layout shift of 0. The vAPI trial (110 pages) and the Vertical Studio trial (48), which do not set `home`, build every file equal to main's build once the stylesheet's name is set equal.
- **Copy page and copy code** (built; Safari not tested). "Copy page" beside the title puts the page on the clipboard as Markdown, and every code block has a Copy button. Adding the buttons moves nothing on the page, and a reader without JavaScript sees no button that cannot work. Proof: in Chrome the clipboard held the 19,218 characters of `/reference/http-api/agents-and-router.md` and then the text of the first code block; no code block moved on any of the 109 vAPI pages at 1280 and 390 pixels wide (2026-11-17); Firefox 161 copied the same page and code block, and so did WebKit 26.6 (2026-11-18); a button that scrolls under the header stays behind it in Chrome, Firefox 161 and WebKit 26.6 (2026-11-18); with scripts off in Chrome the page holds one copy button and it is not displayed.
- **Images that do not move the page** (built). An image has its width and height in the page, loads when the reader comes near it, never grows wider than the text, and a PNG or JPEG is served as WebP. Proof: the 19 screenshots of the Vertical Studio docs are 12.2 MB as PNG and 1.6 MB as built; Lighthouse reports a layout shift of 0 on the page with the most screenshots, in three runs (2026-11-17).
- **Diagrams that follow the theme** (built; Safari not tested). A diagram drawn for light and for dark shows the right file, also after the manual theme switch. Proof: screenshots of the vAPI Agents page in both themes and after the switch; the request log shows the dark file is fetched only when the theme turns dark (Chrome, 2026-11-17); Firefox 161 and WebKit 26.6 show the right file for a light system, a dark system and after the switch.
- **Wide tables stay inside the page** (built). A table wider than the text scrolls sideways inside itself on every screen size, a small table keeps the full width of the text, and a long address or path breaks. The Tab key reaches a table, and the arrow keys then scroll it. Proof: at 1280, 1024, 900, 640 and 390 pixels wide, none of the 109 vAPI pages (205 tables) is wider than the window, and none of the 47 Vertical Studio pages (49 tables) at 1280, 900 and 390; before the change one vAPI page measured 1,337 pixels in a 1280 window and seven pages were wider than a 900 window (Chrome, 2026-11-18). Firefox 161 shows the same on the two pages with the widest tables at 1280 and 900 pixels. Lighthouse scored 100 in all four categories on seven vAPI pages, among them those two, in each of three runs (local run, 2026-11-18). On the vAPI Agents and Router page at 900 pixels, Tab reaches the first table that scrolls and the right arrow scrolls it to its end, in Chromium 153 and WebKit 26.6; WebKit shows no page wider than the window on the two pages with the widest tables at 1280, 900 and 390 pixels; Chromium's accessibility tree lists the table with its rows, column headers and cells (2026-11-18). Not tested with a screen reader.
- **A page for an address that has none** (built; live on verticaldocs.dev). A dead link answers with status 404 and a "Page not found" page that keeps the header, the search and the list of pages. Proof: on the local Workers runtime `/no/such/page/` answered 404 with that page, also for a request with `Accept: text/markdown` (2026-11-18); `content/reference/worker.md` quotes the command. `https://verticaldocs.dev/no/such/page/` answers 404 with that page (2026-11-20).
- **Active section in the table of contents** (built, Chrome only). CSS marks the section being read; Safari and Firefox show a plain list. Proof: tested in Chrome 157, Safari 26.2 and Firefox 151 on 2026-11-17.

## For writers

- **Plain Markdown** (built). One file is one page, one folder is one sidebar group, and a page has three frontmatter fields. Proof: the pages in `content/`.
- **Mistakes stop the build** (built). A broken link or anchor, a search result that opens nothing, a wrong heading level, a `###` with no `##` above it, a code block without a language, HTML in a page, a task list, an image without alt text, from a web address, in a file that is not an image or written in a way the Markdown copy cannot follow, a field over its limit or a folder without an index page fails `pnpm check` with a message that says what to change. Proof: the tests in `scripts/check-dist.test.ts`, `src/core/writing.test.ts` and `src/core/nav.test.ts`.
- **Images in plain Markdown** (built). A writer saves the file beside the page and writes one Markdown line; a diagram per theme is two files named `-light` and `-dark`. Proof: `content/add-an-image.md` shows both on this site.
- **Docs can live in another folder or repository** (built). In the kit's own checkout, `DOCS_ROOT` points `pnpm dev` and `pnpm check` at another content folder; the installed command takes the docs folder as its argument. Proof: the vAPI docs (109 pages, 34 images) and the Vertical Studio docs (47 pages, 19 images), each in a folder outside the project, pass `pnpm check` (2026-11-17); `content/reference/configuration.md` says how for the installed command, and `AGENTS.md` for the kit's own checkout.
- **Docs that update themselves from code changes** (written; run on GitHub only without a model key; phase 3b). A product repository calls `docs-sync.yml` on a push to `main`: an agent without a shell edits the docs, a second job without the model key or a write token runs `vertical-docs check`, and a third refuses any change outside the content folder and keeps one pull request on `docs/sync`. The writing rules and the check come out of the package `vertical-docs`, so no job reads the kit's repository, and a product that has not set the model key gets a run that does nothing. Shown so far: the shell steps ran in a throwaway repository, where a docs change that waited in the pull request stayed in the patch, a file the agent wrote outside the content folder was left out, and the guard refused a patch with a file outside the content folder and a patch with a symlink (2026-11-17). Runs go one at a time, so two code changes close together cannot overwrite each other's docs (a concurrency group with `queue: max`, read in GitHub's documentation), and a run stops when it cannot ask GitHub whether docs changes are waiting. With the package: the two steps that use it ran as the workflow writes them, in a repository that `init` had written, against a local registry that served a packed copy of the kit as `vertical-docs`. The agent's job got the kit's `WRITING.md` from two requests, the package's entry and its file, and installed nothing; the check exited 0 on a page that was edited as the agent would and 1 with `index.html: link "/guide/" points to no file in dist` on a broken one; both steps worked for a product whose `package.json` allows only pnpm, where npm inside the checkout stops with `EBADDEVENGINES`; and from an empty npm cache the check exited 0 while npm ran no install script of a dependency (2026-11-19). Without a key, on GitHub: called from a throwaway branch of the kit's own repository, which has no model key, the run was green, with the three jobs skipped (run 44507167487, 2026-11-19). Not shown: a run on GitHub with a key, which needs a demo repository and a model key.
- **A coding agent keeps the docs in step in its own session** (built; tried with Codex and Claude Code on copies of a product's repository; an agent follows the lines most of the time, not every time). `vertical-docs init` writes a short section to `AGENTS.md` in the root of the repository: when a change to the code changes behaviour that a page describes, read the writing rules, edit the page and run `vertical-docs check`, with the docs folder and `npx` or `pnpm exec` filled in. An `AGENTS.md` that exists gets the section at its end, once, and nothing else in the file changes: it is the one file `init` adds to. `vertical-docs rules` prints `WRITING.md` of the package, because with `npx` and no install that file is at no path a repository can name. No model key and no workflow: the agent is the one in the developer's own session, and `docs-sync.yml` is optional. Proof: the tests "init writes an AGENTS.md that tells a coding agent to edit the page with the code, where the rules are and which check to run", "init adds its section to the end of an AGENTS.md that exists, once" and "rules prints the writing rules of the package" in `src/cli.test.ts`. In a clone of `vapi-network` with the kit packed from the branch, never pushed: `init website` printed `Added the docs section to AGENTS.md` and added eight lines to the end of the 131-line file, Prettier 3.9.6 passed on it with the repository's configuration, and a second `init` changed nothing. On copies of that clone, each agent got a code task that says nothing about docs. Codex (`gpt-6.1-sol`), asked to give `vapi search` a default limit of 10: with the section it changed the CLI reference page in `website/content/` and ran `pnpm exec vertical-docs check website`, exit 0 with 110 pages, in both of two runs; without the section it changed only code and tests. Claude Code (Sonnet), asked to rename an option of `vapi search`: with the section it changed the four pages that name the option and ran the check, exit 0, in both of two runs; without the section it changed the same four pages and ran no check. When the task text began with "In packages/cli", Claude Code changed the pages in one of three runs with the section and gave the stated scope as its reason in another. `rules` was run in one of the seven runs with the section, and three of the seven had an earlier wording of it, two bullets where the three steps are now (2026-11-19). The logs are kept outside the repository. Not shown: an agent in a developer's interactive session, and a repository where the package is not installed.

## For agents

- **A Markdown copy of every page** (built). `/<page>.md` returns the page as Markdown with its title, and an image in it points at the full address of the file the site serves. Each page links to its copy at the end of the page and in a `link rel="alternate"` element. Proof: `curl http://localhost:4321/index.md` on the preview of a starter folder, quoted in `content/reference/agents.md`; all 36 image links in the 109 Markdown copies of the vAPI docs are full addresses of files in the build (phase 3b build, 2026-11-17), and all 19 in the Vertical Studio docs were files in the phase 3a build; the tests "points each image outside code at the URL the site serves it at" and "throws for an image of the page that it cannot find in the Markdown".
- **`llms.txt`** (built). One file lists every page with its description, grouped by folder in sidebar order, linking the Markdown copies by their full address. Proof: `curl http://localhost:4321/llms.txt`, and the test "writes llms.txt in sidebar order, one section per folder, linking the Markdown copies by their full address" in `src/core/llms.test.ts`.
- **`search.json`** (built). Every section of every page as `{ url, title, heading, text }` in one static file, usable with `curl` and `jq`. The check follows every URL in it. Proof: 53 records for 11 pages, 7.2 KB gzipped (2026-11-17); the test "fails for a search result that points to no page or to no heading". At real size: 703 records for the 109 vAPI pages, 141 KB gzipped, and ten results 44 to 66 ms after the search opens (scripted key press and query, local server, desktop Chrome, three runs).
- **The same search in a terminal** (built). `pnpm run search "<query>"` prints the sections the site shows, in the same order, as plain text or JSON, for the last build or for a deployed site. Proof: the query `sidebar` gave the same nine URLs in the same order in the dialog and in the terminal (2026-11-17); the tests in `src/cli.test.ts`.
- **An MCP server** (built; live on verticaldocs.dev). `/mcp` on the Worker has two tools: `search_docs` returns the sections the site search shows, in the same order, and `get_page` returns the Markdown copy of a page. The server keeps nothing between calls. Proof: the tests in `src/worker.test.ts`; on the local Workers runtime with the vAPI docs, Claude Code and Codex each searched for "hosted mcp", got the same three URLs as `pnpm run search`, and fetched the first page (2026-11-17). `content/reference/worker.md` quotes a call. On `https://verticaldocs.dev/mcp` the server lists both tools, `search_docs` for "home page" returned the "Home page" section of the configuration page first, and `get_page` answered 200 (2026-11-20).
- **Markdown for `Accept: text/markdown`** (built; live on verticaldocs.dev). A page URL answers a request with that header with the Markdown copy of the page. Proof: the test "answers Accept: text/markdown on a page URL with the bytes of its Markdown copy"; on the local Workers runtime all 109 pages of the vAPI docs returned the same bytes as their `.md` file (2026-11-17). `https://verticaldocs.dev/` answers that header with the same bytes as `/index.md` (2026-11-20).
